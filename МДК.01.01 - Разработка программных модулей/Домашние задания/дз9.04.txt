 Упрощённая Clean Architecture
Главная идея:
Код делится на слои, зависимости направлены строго внутрь. Бизнес-логика не знает о внешнем мире (БД, API, UI).

Основные слои (от центра к периферии):

Domain (Ядро)

Что: Бизнес-сущности, основные правила.

Правило: Не зависит ни от чего (нет UI, БД, API).

Application (Use Cases)

Что: Сценарии использования, конкретная бизнес-логика.

Задача: Описывает, что делает система.

Infrastructure (Инфраструктура)

Что: Работа с БД, API, файлами.

Особенность: Зависит от интерфейсов (можно легко заменить).

Presentation (UI)

Что: Интерфейс пользователя, кнопки, экраны.

Правило: Не содержит бизнес-логики, только вызывает Use Cases.

Направление зависимостей:

UI → Use Case → Domain

Infrastructure → Use Case / Domain

Ключ: Внешние слои зависят от внутренних, но не наоборот.

Связь с DIP и DI:

DIP (Принцип инверсии зависимостей): Внутренний слой определяет интерфейс (например, репозитория).

DI (Внедрение зависимостей): Внешний слой передаёт реализацию этого интерфейса внутрь.

Плюсы и минусы:

Плюсы	Минусы
✅ Слабая связанность	❌ Больше кода
✅ Удобно тестировать	❌ Сложнее на старте
✅ Легко менять компоненты	❌ Избыточно для маленьких проектов
✅ Масштабируемость
