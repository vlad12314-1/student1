1. Проблемы использования SQL в GUI (Плохая практика)
Когда SQL-запросы пишутся непосредственно внутри кода интерфейса (кнопок, окон), возникают следующие трудности (Рисунок 1):

Сложность тестирования: Нельзя проверить логику интерфейса без реальной базы данных.

Сложность смены БД: При переходе с одной СУБД на другую (например, с MySQL на PostgreSQL) придется переписывать весь код.

Превращение кода в «кашу»: Логика отображения данных смешивается с логикой их получения и изменения.

Нарушение принципов: GUI начинает отвечать за то, за что отвечать не должен.

2. Сравнение подходов (Рисунок 2)
Плохо (❌)	Хорошо (✅)
SQL-код находится внутри обработчиков кнопок (слотов).	Существует отдельный слой для работы с БД.
SQL вперемешку с GUI-логикой (отрисовка, события).	Для каждой операции с данными создается отдельный метод.
Стандартная последовательность обращений (хороший подход):

GUI (Кнопка) → Вызов метода DAL → DAL выполняет SQL → Возврат данных → GUI отображает результат.

3. Что такое Data Access Layer (DAL)
Data Access Layer (DAL) — это промежуточный слой приложения, который:

Знает, как работать с БД (содержит подключения, запросы).

Скрывает SQL от остального кода (интерфейс не знает про SQL).

Предоставляет удобные методы для работы с данными (например, getUserById(), saveOrder()).

4. Архитектура приложения (Рисунок 3)
Принцип: «Каждый слой отвечает только за своё».

Слой представления (GUI/UI): Отвечает за отображение и ввод данных. Не знает про SQL.

Бизнес-логика (Domain/Service): Отвечает за правила обработки данных.

Слой доступа к данным (DAL / Repository): Отвечает за сохранение и загрузку данных. Содержит SQL.

5. Repository или DAO (Сравнение)
В рамках DAL используются два похожих, но разных паттерна:

Характеристика	DAO (Data Access Object)	Repository
Способ доступа	Прямой доступ к таблицам.	Работает с сущностями (объектами).
Принцип	1 класс = 1 таблица (CRUD операции).	Скрывает детали хранения (может объединять несколько таблиц).
Уровень	Ближе к инфраструктуре БД.	Ближе к бизнес-логике.
6. Зачем нужен Repository (Итоговая выгода)
Использование DAL (Repository/DAO) позволяет:

Убрать SQL из GUI — интерфейс становится чище.

Уменьшить дублирование — один и тот же запрос пишется один раз.

Сделать код читаемым — метод getActiveUsers() понятнее, чем строка SELECT * FROM users WHERE status=1.

Упростить поддержку — если нужно изменить БД, меняется только DAL, а кнопки остаются без изменений.
